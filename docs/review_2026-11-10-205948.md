# Review of the vehicle footprint design, rev 2

Reviewed: 2026-11-10 20:59:48 EST  
Document: [2026-11-10-footprint-design.md](2026-11-10-footprint-design.md)

The proposed separation between locators, smoothing, and polygon construction is useful. Resolve the three P1 pipeline contracts before implementation; otherwise normal missing-data cases can abort the run or silently discard the intended M7 measurements. P2 comments address other observable behavior and API gaps.

Scope: reviewed the design against the current `smooth`, `speed`, and `transform` implementations and their tests. The Windows study directory, source documents, model artifacts, and pinned run inputs were not available in this workspace. Algorithm parity, study statistics, and the M7 freeze state therefore remain unverified. References below use the reviewed document's line numbers.

## 1. [P1] Define how invalid projections enter the initial grid

**Location:** §9, lines 346–350; §5.2, lines 147–149; §7.10, line 313.

The design first computes M1 only for valid projections, then calls `segment()` on those points. However, `segment()` is described as exposing the existing `_grid`, whose `segments.prepare()` rejects any non-finite position. The new NaN allowance applies only after a grid already exists. Passing an invalid M1 row therefore raises; removing it first loses the promised input row and can turn its frame into an ordinary fill. An entirely invalid track has no way onto the grid at all.

Specify segmentation and reinsertion rules for invalid rows, including invalid prefixes, suffixes, and whole tracks. Preserve their identity and `projection` failure without inventing a ground measurement. Add cases for one invalid row between valid observations and a track with no valid projections.

## 2. [P1] Specify the complete reused-grid merge and coordinate contract

**Location:** §5.2, lines 147–151; §7.11, lines 318–331; §11.3, lines 446–453.

`locate()` returns `seg` and `fill_reason`, and its output is passed directly to the smoother. The current `_finish()` rejects those columns as clashes; a focused check reproduced that `ValueError`. Merely adding a `grid` argument does not resolve this merge conflict.

The existing grid also contains M1-derived `x_raw`, `y_raw`, `x_obs`, `y_obs`, and a local-coordinate `origin`. Reusing those values would leak the segmentation points into another method, especially when `smooth_segment()` returns raw positions for a segment with fewer than two measurements, or when MA/SG uses the raw interpolated positions.

Define which fields are structural, how supplied `seg`/`fill_reason` are validated and preserved, and how every call replaces observations and constructs method-specific raw positions in the grid's coordinate frame. Define the result for a segment with no successful locator rows. Test reuse with deliberately offset M1/M6 positions, a large UTM origin, and an entirely failed method; the existing same-positions equality test cannot detect stale M1 values.

## 3. [P1] Separate row provenance from measurement admission

**Location:** §7.7, lines 280–285; §7.11, line 318; §5.1–5.2, lines 140–149.

Rows inserted into a gap retain `interp = 2`. M7 can subsequently admit a finite pose and covariance on such a row, but the current RTS path counts only `interp < 2` as usable and explicitly clears observations on all other rows. Under that rule, the pseudo-measurement is discarded even though `fp_source` says M7 supplied it. Finite M7 observations at upstream-filled rows also need an explicit rule for whether `fill_scale` further inflates their already scaled covariance.

Introduce an explicit measurement-validity rule or mask independent of the original row's `interp` provenance. Specify covariance scaling for each support type. Test that an admitted M7 point on an inserted gap frame changes the smoothed result and that disabling admission removes that measurement.

## 4. [P2] Handle sparse orientation observations and leading missing positions

**Location:** §10.2, lines 369–374; §5.2, line 149; §7.8, line 300.

The design calls `rts_smooth()` directly for orientation, but that function indexes the first two finite observations without a guard. Focused calls with zero or one observation both raised `IndexError`. Zero native orientations is routine for an M2 track; a single successful M6 row is also valid input. The positional wrapper avoids the crash through raw fallback, but its no-measurement behavior still needs the contract requested in comment 2.

Also address leading missing measurements: `rts_smooth()` constructs its initial state at the first observed position but starts filtering at frame zero without moving that state back to frame zero. The new grid API makes these prefixes possible.

Define zero/one-observation orientation behavior and initialization at the correct timestamp. Test no native axes, one native axis, and a known constant-velocity trajectory with a missing prefix.

## 5. [P2] Preserve usable native axes when a vehicle never moves

**Location:** §10.1–10.2, lines 362–376; §10.4, line 387.

A never-reliable segment gets NaN motion heading, yet every native orientation is folded to an axis and then directed toward that heading. A stationary vehicle with excellent M6 cuboids or a passed M7 solve can therefore have a valid centre, dimensions, and axis but no defined final orientation. The statement that folding loses nothing does not cover this case. This matters for stationary vehicles in later PET/conflict calculations.

Define the no-motion case explicitly. A rectangle can be constructed from an undirected axis; if front-left corner semantics require a front, preserve a supported native direction or mark front direction as unknown separately. Add a stationary vehicle case and a track that starts stationary before moving.

## 6. [P2] Include the existing OpenCV dependency in the lazy-import plan

**Location:** §2 anti-goals, line 68; §6.1, lines 157–158; §13, lines 494–495; §14.2, line 550.

The current `tssa.transform.homography` imports `cv2` at module load, uses `cv2.RANSAC` as a constructor default, and uses `cv2.perspectiveTransform` even for projection. Blocking `cv2` and importing `tssa.transform` reproduced a `ModuleNotFoundError`. Making only the new detector and camera imports lazy does not let an M2 run use the package's existing homography classes without OpenCV.

Either include the existing homography module in the dependency refactor, or narrow the guarantee to an externally supplied OpenCV-free transform. Make the lazy-import test exercise the supported public construction/loading path, and reflect the choice in the build order.

## 7. [P2] Supply image dimensions and an explicit distortion adapter

**Location:** §4.2, line 112; §7.10, line 314; §8, lines 336–337; §11.1, lines 414–417.

The accepted homography protocol requires only projection methods, but border flags and the camera's image-centre prior also require image width and height. Neither `VehFootPrinter` nor `PinholeCamera.fit()` accepts image dimensions. `DistortedHomography` has `image_size`; `HomographyTransform` and arbitrary compatible objects need not have it. Similarly, `HomographyTransform` currently has no `undistort()` or `distort()` methods despite §4.2 treating them as identities.

Define an adapter with identity distortion for ordinary homographies and a source for image dimensions, such as an explicit argument with a documented metadata fallback. Specify that camera fitting and consistency compare points in the same undistorted pixel space. Test an ordinary homography as well as a distorted one.

## 8. [P2] Normalize speed units before applying the heading threshold

**Location:** §10.1, line 363; §11.3, line 453.

Angles from `vx, vy` are unit-independent, but the reliability threshold of 3 mph is not. The public constructor allows a custom `SpeedCalculator(units="metric")`, and `polygons()` accepts its output. A focused 2 m/s example produces 4.474 mph or 2.000 m/s; directly comparing either speed to 3 gives opposite reliability decisions for the same motion.

Convert the threshold using the calculator's units or the output's `speed_unit` metadata, and define behavior if that metadata is absent. Test that metric and imperial outputs produce the same reliability mask and orientation.

## 9. [P2] Make native-only comparison exclude M7 pseudo-measurements

**Location:** §7.7, lines 281–285; §7.8, line 300; §11.2, lines 436–437.

`compare(fallback=None)` promises a native-only product, while `admit_kinematic` defaults to true and M7 admits unsupported rows before fallback selection. Removing the fallback locator alone therefore still feeds M7-derived pseudo-measurements into the smoother, contrary to the stated native-only meaning and the distinction used for comparisons.

Specify whether native-only comparison disables admission automatically or requires an explicit comparison option. Verify that a kinematic row has no measurement in native-only mode and retains `kinematic` support when admission is requested in the end-to-end mode.

## 10. [P2] Resolve the contradictory comparison row-count guarantees

**Location:** §11.2, line 438; §14.2, line 549.

The API says M7 car rows are skipped, but the proposed test requires every input row once for each comparison method. These give different output shapes and affect downstream paired comparisons.

Choose one contract. To preserve the general row guarantee, retain ineligible rows with an explicit reason such as `class_ineligible`, and define whether the requested fallback applies to them. Test a mixed car/bus input and `only_tracks` filtering.

## 11. [P2] Give the detector runner the configuration needed to select rows

**Location:** §6.4, lines 178–184; §11.1, lines 403–407.

The default detector row selection depends on each class's locator chain, but `detect.run()` receives neither `FootprintConfig` nor a printer. In the public example, detection runs before the printer is constructed. The runner cannot know that custom chains require M5 masks for cars, or that another configuration needs no masks at all. It also needs the complete frame's boxes for the one-to-one matching rule even when requested output rows are restricted.

Pass the relevant configuration/required-table selection explicitly, or define a configuration-independent default that processes all supplied track rows. Keep frame-wide matching context separate from requested output/cache rows. Test a custom car chain containing M5 and restricted output selection in a crowded frame.

## Validation and source handoff

Focused runtime checks used `PYTHONPATH=src .venv/bin/python` and confirmed the existing column-clash error, zero/one-observation RTS errors, OpenCV import dependency, and speed-unit difference described above. No package code was changed, and the full test suite and external NW-clip validation were not run for this document review.

Before porting, make an immutable study snapshot available with the referenced source documents, source-file hashes, exact settings, fixture/cache schemas, and pinned dependency versions. Per-file docstrings added at port time record provenance, but cannot by themselves establish that all copied files came from the same validated M7 state. This is especially relevant while Q6 remains open.
