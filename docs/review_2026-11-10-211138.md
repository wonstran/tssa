## 1. [P1] Exempt admitted M7 gap states from the box-projection gate explicitly

**Design locations:** §7.7, lines 343–346; §7.10, line 386; §9, lines 431–437.

Section 7.7 explicitly admits M7 pseudo-measurements on inserted `interp = 2` frames. However, §7.10 still says every locator fails a row whose bbox-bottom projection is non-finite. Inserted frames have no input box or Jacobian. A focused check of the current smoother confirmed NaN bbox fields on inserted rows, and the new structural-only grid does not supply replacement boxes. Applying the shared gate therefore rejects the very rows §7.7 promises to admit. Changing the smoother's `interp` handling fixes only the later half of this path.

The study distinguishes these cases: `grid.py` marks inserted frames `proj_valid = False`, while `products._product()` admits M7 kinematic states independently of that native-point gate. Its admission predicate checks solve success, kinematic support, and finite pose/covariance; it does not require a valid bbox projection.

**Requested change:** separate native box-observation gating from M7 pseudo-measurement admission. Explicitly distinguish an inserted frame with no box from an original row whose projection was rejected, and state whether admission may override rejection on the latter. Preserve the stated `seg = -1` exclusion. Do not create a box or a box-derived covariance for an admitted state.

**Validation:** exercise `locate()` through `estimate()` with an actual inserted gap frame and a passed M7 solve. Assert that its own covariance reaches the smoother despite absent box/Jacobian fields. Also test an original invalid-projection row and a `seg = -1` row. The proposed smoother-only admission test cannot detect this earlier rejection.

## 2. [P2] Correct the direction of the M7 width-hold threshold

**Design location:** §7.6, line 311.

The design says width is held when the silhouette resolves **less than 0.3 ft/px**. The study implements the opposite inequality:

```python
w_held = w_ft_per_px > M7_W_HOLD_FT_PER_PX
```

This is in `m7.py`, line 1086, with `M7_W_HOLD_FT_PER_PX = 0.3` in `settings.py`. Higher feet per pixel means coarser width resolution. The study's build notes also specify holding width when resolution is coarser than the threshold. Following the design's inequality would hold the better-resolved widths and fit the poorly resolved ones, changing both dimensions and their source labels.

**Requested change:** say `w_ft_per_px > 0.3`, including the strict boundary and the infinite-resolution-value case used when width has no silhouette effect. Keep the source code's rule authoritative.

**Validation:** cover values below, exactly at, and above the threshold, plus infinity; compare the hold decision with the study.

## 3. [P2] Choose one rule for explicit admission overrides in native-only comparison

**Design locations:** §11.2, lines 552–556; related §7.8, line 362. **Response:** item 9.

The native-only bullet says admission is off “whatever `admit_kinematic` says,” while line 556 says an explicit argument overrides either default. The response likewise promises an explicit override. Thus `compare(fallback=None, admit_kinematic=True)` has two specified results. The single-locator/native-only claim in §7.8 also omits the admission distinction.

**Requested change:** specify precedence once. Either native-only always disables admission and a conflicting override is rejected, or explicit `True` enables admission and the resulting product is described accordingly. Align the response, single-locator explanation, and API tests with that choice.

**Validation:** test `fallback=None` with `admit_kinematic=None`, `False`, and `True`, including support/source flags on the kinematic row.

## 4. [P2] Reconcile the new micrometre round-trip test with millimetre output rounding

**Design locations:** §5.2, line 193; §14.2 test 3, line 690; backward-compatibility promise at line 163.

The new test requires positions near UTM coordinates to round-trip to `1e-6 m`. The existing smoother rounds its added numerical output columns to three decimal places in `_finish()`. A focused constant-velocity example starting at `5200000.123456 m` returns `5200000.123 m`, an error of approximately `0.000456 m`. Correct origin handling alone cannot satisfy the proposed public-output tolerance.

**Requested change:** identify what is being tested. If this is an internal local/world conversion check, assert `1e-6 m` before output rounding and test the public result at the documented rounding tolerance. If segmented mode is intended to retain more precision, specify that behavior explicitly while preserving the legacy path's rounding. Avoid changing all existing output precision incidentally.

**Validation:** use coordinates with more than three decimal places and absolute tolerances with `rtol = 0`; a default relative tolerance at UTM scale can hide the discrepancy.
